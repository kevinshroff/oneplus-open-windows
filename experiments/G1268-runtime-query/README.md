G1268 is an offline query-only Windows ARM64 driver candidate. DriverEntry and the default status client perform no monitor call. Only an explicit fixed once IOCTL queues the real production SMC thunk. No hardware/runtime qualification is claimed.

Fixed transport

The sole profile is FAST INFO64: x0=c2000601, x1=1, x2=02000c1b, x3..x7=0. The IOCTL contains only version/tag, never caller-controlled monitor values. There is no setter, normal/legacy/HVC fallback, shared buffer, cache maintenance, TPM/RPMB, GPU or MMIO path. The actual thunk is source/smc_fast_info.S, not a stub. It preserves Windows x18/nonvolatile/stack conventions and emits ARM64 unwind records. It retains returned x0..x7 and resumes only exact 64-bit INTERRUPTED=1, including the returned x6 continuation. Returned registers are not reset between transitions. Full raw final x0..x7 and transition counters are reported; intermediate interrupted register images are overwritten by the next returned transition.

x0=0 is transport completion; x1 then means available/nonzero or unavailable/zero. Negative returns are raw errors; -12 is busy without retry, -1/-4 unsupported without fallback. WAITQ2/3 and other positive or malformed states remain unknown/incomplete, retain rundown and prohibit replay. No secure cancellation, bounded monitor latency, finite SMC watchdog or WAITQ completion support is invented. Completion and interrupted continuation retain strict full 64-bit equality. Error classification accepts only zero-extended or sign-extended negative int32, matching actual QcTrEE_i signed-w0 tests and primary qcom_scm_remap_error(int). Both 00000000fffffff4 and fffffffffffffff4 are busy errors without replay; raw bits remain unchanged. Malformed upper bits retain unknown state. Unexpected upper bits cannot manufacture completion or continuation.

Lifetime and admission

The device DACL permits SYSTEM/Administrators only. Status requires READ access; explicit query requires READ|WRITE. The worker runs PASSIVE with a sleepable mutex and no spinlock held across SMC. The short state lock only publishes snapshots. Accepted IRPs are not canceled by caller timeout; a stuck monitor/continuation can hold a system work item indefinitely. This is a real tradeoff, not a finite latency guarantee. Another status handle can inspect stable EXECUTING state without issuing a call; partial raw frame writes are not published as a completed result.

DriverUnload is NULL from entry. The component is deliberately resident until reboot even after an inert load or terminal result. This prevents unload/reload from replaying the one-query limit within the boot; the fixed device name also rejects another simultaneous instance. There is no service installer or persistent automation. Root must use a demand-start/manual service (Start3), with no automatic recovery actions. Unloading, freeing, stop/reload or an application timeout is not a recovery mechanism for an incomplete call. The once limit persists for the life of this device/driver, not in a registry marker.

A private mutex does not serialize unrelated Windows SCM clients. The direct FAST64 conduit, preserved nonvolatile ABI, monitor behavior during INTERRUPTED, competing firmware clients and platform support still need root's actual compiled review and explicitly selected hardware qualification. There is no asserted CPU0 requirement and no new affinity policy; actual installed transport does not pin in its primitive. Neither successful INFO nor four VALUE arguments qualify an aperture setter or its asynchronous/persistent side effects.
